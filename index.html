RPU (Robot Processing Unit)

We etch the robot’s world model into silicon.

Real‑time world‑model inference, inside the head, on 40 watts.

Detail

Humanoid control is converging on world models: a fourteen‑billion‑parameter diffusion transformer that imagines the next two seconds, acts, and re‑plans five times a second. Today that takes a datacenter. We build the chip that runs it in the head.

01 — The requirement

Real time, on board,
in any environment.

A two‑hundred‑millisecond hard deadline inside a robot head — deterministic, with no jitter.

Detail

Being fast on average is not the requirement. The answer has to arrive on the same schedule every time, and it has to behave the same in a warehouse, a basement, or a field with no signal. A robot’s competence should not depend on its connection.

That budget has to be met in a head whose neck path can reject roughly forty watts. Throughput is the easy half. The hard part is that the deadline and the power ceiling pull against each other.

  • 5 Hzre-plan rate
  • 40 Wmodule power in-head, matched to the Jetson Thor module
  • 14 Bparameters to serve

02 — What it costs today

We built the wrong
solution first.

Control rate took two B200s in a datacenter and a custom QUIC relay. That puts the network inside the control loop.

Detail

We have built inference stacks at frontier humanoid robotics companies. Reaching control rate took the entire arsenal: sixteen‑to‑three‑step distillation, classifier‑free guidance split across two B200s, velocity caching between diffusion steps, graph capture to suppress kernel‑launch overhead, and train‑time chunking to fit the streaming regime. It worked — at two kilowatt‑class GPUs per robot.

So we built the other half of the obvious answer too, down to a custom media‑over‑QUIC layer streaming observations up and action chunks back. Building both is what made the mistake obvious. No amount of transport engineering makes a wireless round trip predictable enough to design against. Humanoids cannot scale if every robot depends on a remote GPU cluster and perfect connectivity.

03 — The bet

Etch the dataflow.
Start with a systolic array.

Fixed graph, fixed shapes, weights resident, deterministic latency. The bet Google made with the TPU — aimed at the head.

Detail

There is nothing exotic about the first chip. It is a systolic array at the edge, the same bet Etched made for the datacenter and Groq made with the LPU. Nobody has made it for the robot. A fixed graph and fixed tensor shapes buy static scheduling, no kernel dispatch, and timing you can put in a safety case.

The generality is what costs you. A general‑purpose SoC spends die area and power on rasterization, display, and a CPU complex a fixed policy will never call. Reallocate that to tensor arrays and on‑chip SRAM and the same watts do a lot more useful work.

04 — Evidence

At forty watts,
only joules matter.

The datacenter fights the memory wall. A robot head fights power. At 40 watts this workload is compute-bound, so the only lever that matters is energy per useful operation — not more bandwidth.

Detail

Counting a DreamZero-class model gives about 16,000 FLOPs per byte fetched, against a Jetson Thor roofline near 3,800 — roughly 4× inside the compute-bound regime. Adding memory bandwidth does not move the constraint; energy does.

The gain comes from deleting the overhead of programmability. On a general-purpose chip only about 6 % of energy reaches the units doing arithmetic, and a single control chunk launches roughly 1,200 GPU kernels. A purpose-built chip hard-codes that schedule, streams weights predictably, and keeps intermediates local. TPUv4 already delivered 1.6–3.2× higher performance per watt than an A100 on the same process node, so the near-term ask has been done before.
